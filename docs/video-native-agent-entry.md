# 用原话启动 GrowthTest 正式视频制作

在当前 GitHub 默认分支的干净检出中打开工作台。仓库身份为 `geniusdapeng-collab/workloom-growthtest`。按 [Agent 接入指引](AGENT-CLIENTS.md) 准备依赖、数据库、供应商和授权成员会话。客户端首先核对 `/health` 的产品、实例和源码提交，再用 `access.me` 核对成员与工作区。这个入口面向有可核实源码版本的服务；没有相同 `sourceCommit` 的运行实例需要由部署方按同一源码版本启动。

## 从用户原话取得正式前期

把原话放在 `intent`。仅在已知时附上 `durationSec`、`platform` 或 `product`。指定的人物、商品、情节和平台来自本次任务。镜头划分、逐镜时长、提示词和生成资格由系统产生。选择营销片时走商品情报和 G1；叙事片走同一工作台的叙事流程。解释片使用专用工位。

需求正文最多 12,000 个 Unicode 字符，扩展汉字也按一个字符计数。每个镜头最终提示词最多 3,000 个 Unicode 字符，进入正式审核前完整校验。客户原始需求保持完整；生成器可在审核前按字段精炼和压缩提示词，随后审核完整正文，已通过的正文与摘要保持绑定。

正式前期直接连接本次配置的文字模型和真实检索通道。RDAS 和独立验收转发器只用于开发验收，其历史调用次数、累计 token、金额、查询数和运行时长配额不作为正式作业的启动或完成条件。正式前期持续处理各工位，不因整轮或单阶段耗时而停用模型；单次网络请求仍有超时和结果对账，已发送但结果未知的请求保留原执行身份。

营销来源审核会核对完整型号、版本、时间和每一条引用。可选事实有未解决冲突时可以排除该事实，原始来源仍完整留档；媒体报道保留来源归属。若真实评审指出语义错误，提取器按同一批原文和完整诊断修正一次，再接受同样的完整审核与 85 分门槛。两版提取、正文和裁决都留档；结果未知或审核服务异常时先对账。

模型返回的结构或逐项引用有误时，系统保留原始提取和真实校验诊断，按同一批原文修正一次，再完整校验和审核。已经明确不支持的最终镜头会带着原裁决交回生产作者重写，并重新接受 G6 和逐镜事实审核；前面已通过的工位继续复用。相同坏镜头不能反复付费重审。只有审核服务等基础设施故障时，保留原作者成果继续审核；模型结果或归档回执待核实时先核对原执行。

需求洞察保留客户原文与创作建议的区别。客户没有指定的年龄、性别和消费水平保持未指定；受众兴趣推演会明确标为创作假设。营销片仅在客户原文明示时列出具名作品参考，其他情况写可执行的视听手法。场景总数按实际片头、主体和片尾逐段计数，已确认的时长和画幅同时约束制作画像及后续 PRD。

下面用本机独立源码服务的 [成员会话桥接](AGENT-CLIENTS.md) 示范。将作业文件放在仓外的私有目录，保留至交付结束。已授权的远程源码实例可直接用 `node scripts/workloom-video.mjs`，运行环境须提供已核对的 `WORKLOOM_BASE_URL`、`WORKLOOM_DESKTOP_INSTANCE_ID` 和成员令牌。

```bash
mkdir -p "$job_root"
printf '%s' '{"intent":"做一条20秒的雨后山间民宿短片，只拍空景，用于抖音","durationSec":20,"platform":"douyin"}' \
  | node scripts/workloom-source-session.mjs video -- start --input-file - --job-file "$job_root/job.json"
node scripts/workloom-source-session.mjs video -- status --job-file "$job_root/job.json"
```

- `clarify`：按返回的缺项补齐业务资料。
- `awaiting_approval`：经同一实例的正式审批工位处理返回的门和审批 ID。
- `preproduction_ready`：返回当前项目、运行、前期 attempt、镜头原文摘要、时长与管线。开工前核对人物、商品、平台及已知预算、使用权和供应商接收条件。
- `start_unknown`：保留工作单和原实例。先查立项记录；重复启动可能创建第二个项目。单独的导演预览或已有镜头稿入口各有其合同。

## 只交付已通过评审的提示词

客户明确把交付范围限定在提示词时，在启动 JSON 添加 `"purpose":"prompt-review"`，同时给出创作目标时长。系统仍负责分流、编剧、分镜、G6 提示词审核，以及营销任务的来源和逐镜事实审核。此用途在立项时固定。它推迟定妆照、完整预生产和渲染，不触发图像或视频生成。

用同一工作单回读 `prompt_review_ready` 后导出原始审核正文和来源回执：

```bash
node scripts/workloom-source-session.mjs video -- status --job-file "$job_root/job.json"
node scripts/workloom-source-session.mjs video -- prompts --job-file "$job_root/job.json" --out "$job_root/prompt-review.json"
```

导出文件含项目、运行、阶段、尝试编号和正文摘要，须放在任务私有目录。回执标记 `renderAuthorized:false`。出片需要走正式制作流程的素材授权、定妆照、完整预生产和预算审核。

提示词评审被打回或工位发生已核实的失败后，在原实例使用 `video -- resume-prompts --job-file "$job_root/job.json" --out "$job_root/review-continuation.json"`。它核对最新失败运行和原需求，在同一项目内生成关联工作单。已通过的来源、主题、需求洞察和 PRD 按原始产物摘要、审核证据及依赖接续；已完成的剧本与制作工件也写入持久断点。失败工位或依赖变化的工位重新执行，来源过期时刷新来源。收到结果未知时先查原项目与模型台账。使用续跑工作单查询新运行和导出。

G6 明确拒绝时，续跑核对原项目、运行、时间与同一输入的结算状态，把真实裁决交回原生生产作者；定妆照的预期推迟不会盖住实际拒绝原因。新裁决保留完整模型结果；旧记录只按当时已保存的拒绝事件读取，不补造缺失的证据。每镜作者在正常生成和缺字段补齐时都接收完整源动作与叙事职责，冻结需求和已核实返工诊断优先于冲突的技能或早期设计。人物仅限源剧本与本镜合同已声明的参与者；身份参考资料用于固定已登记人物，不被当作全场人数上限，没有图片参考时如实保留文字依据。

已结算的原生运镜失败也会带着完整诊断和冻结的原始需求交回生产作者。系统读取原运行的完整失败档案，并核对原运行身份、摘要、分类、时间和同一输入的结算回执；不会只把数据库中的短错误摘要当作完整诊断。后续已知基础设施失败会保留这份返工依据。作者仍须完整执行所需动作和先后顺序，不能靠虚构切镜动机或场景标记通过检查。此类反馈会按现有机制重新执行原生生产相位，已通过的前序来源、主题、洞察、PRD 和可复用剧本保留；不承诺零模型调用。完整生产、G6 与营销逐镜事实审核继续执行，结果未知或归档回执未核实时仍先对账。

原生生产返回已结算但无法解析的结构化正文时，系统可沿用完整请求、结构和同一模型纠正一次输出格式；纠正请求使用独立的单次超时，并须取得新的同模型响应回执。网络结果未知、HTTP 拒绝或缺少结算回执时不追加这种纠正。营销镜头的规则来源投影不视为原生作者结果，缺失原生方向字段的镜头须重新生成。每个有效的单镜修复在处理下一坏镜前写回原有断点；后续失败时保留此前的原生产物，不从简化规则稿补造字段。

原生音频中的“禁配乐”“禁台词”等明确禁止表达按约束保留原文；实际声音事件仍须满足冻结声音合同，片头只有在校验通过后才写入完成断点。

原生营销镜头按作者已经写出的运镜与灯光继续制作。快速动作与运镜、平静情绪与灯光，以及从场景词推断室内光源或自然光的建议记录为诊断，交由作者和完整审核裁决。生产写入策略进入宿主及原生断点的身份计算；升级后保留旧产物，按当前策略决定复用和重作。

逐镜作者接收完整源镜头计划，以及前面实际完成的原生镜头草稿。动作职责、人物身份与服妆、道具状态、位置和转场两侧由这些真实上下文衔接；不能在后一镜重新执行前镜已经完成的一次性动作。原始断点恢复会补回已保存的草稿，单镜返修会参考当前实际已有的其他镜头。源计划、草稿和历史诊断都不代替质量批准，也不直接拼进交付正文；不同作业使用各自的上下文。

G6 按原需求与完整提示词核对实际参与者和文字。已登记身份参考资产的数量不代表镜头总人数；必需披露与尾帧文字也不自动成为排他清单，原文明示的人物、文字禁令仍须执行。允许的虚构胜利不等于真实战绩、人物背书或商品性能事实。正文中的结构化镜头合同仍是待审证据，不能作为自身质量或媒体授权的证明。

从原生断点恢复时，系统补回与首次执行相同的蓝图上下文，早期相位同时恢复镜头引用。已完成融合的镜头仍按原逐镜凭据核对完整蓝图与技能登记摘要，核验通过才可复用。营销稿在审核前先按完整原生字段重建，再检查实际交付正文的 3,000 字符上限。片头五字段的可用字数来自同一最终正文的剩余容量，由原片头作者生成完整而紧凑的内容；不截断原生动作或片头正文。片头只有在完整字段与最终容量均合格时才保存完成，相同输入下保留已完成的生产工位，再接受 G6 和逐镜事实审核。

升级前的历史工作单可能没有完整工位断点。历史审核明确打回的作业仍可显式重跑；历史程序故障须先核实原模型请求，再记录结算状态后接续。本次执行会创建完整断点，保留历史产物与原始审核的运行编号。

## 从同一作业渲染并交付

选取运行实例目录里可用的模型，在同一项目使用经核对的 [标准后期设置](video-standard-post.md)。设置声明封面、字幕、调色与可选既有音乐，以及字体和输入摘要。封面平台须与同一正式工作单记录的平台一致。制作工作台复用已登记设置；缺授权或缺必要素材时保留当前回执。设置文件须在首次渲染前就绪。以下金额来自本次批准，由执行环境传入。

```bash
node scripts/workloom-source-session.mjs video-deliver -- \
  --job-file "$job_root/job.json" --work-dir "$job_root/production" \
  --model "$render_model" --max-estimated-cny "$approved_cny" \
  --post-settings "$approved_post_settings" --out "$job_root/delivery"
```

已授权远程源码会话可在仓库根运行 `pnpm exec tsx scripts/tools/deliver-studio-video.mts`，沿用同样参数。仅核对并采用已有原片时省略金额上限。收到已有任务 ID、生成已受理或回执未知时保留同一工作单和 `.render-start.json`。仍在等待供应商完成或入库时，去掉金额参数，增加 `--poll-existing` 继续原项目的已登记任务。受理后的补记账及未知任务按 [渲染恢复指引](video-render-task-recovery.md) 核对原请求。

自动首轮提交只用于档案已证明 G5 无人物或商品参考的叙事项目。需要人物或商品参考时，正式工位须先把授权素材与每镜供应商请求绑定，不能降成纯文字生成。标准后期可从同一运行的已绑定、已完成、已入库原片继续。

出片入口通过同一前期签发资格和提交请求，保存原任务回执。它通过同一工作区的签名媒体地址取得原片，并核对入库字节、完成事件、资格签名、脚本版本和当前前期。标准后期使用原镜顺序、完整画面及可用的原生音轨，保留实测时长。当前发布前复查服务回执与本地成片、封面、字幕和导出摘要。只有 `delivery_verified` 且交付目录可回读时才交付文件。发布到平台走另外的正式授权入口。
