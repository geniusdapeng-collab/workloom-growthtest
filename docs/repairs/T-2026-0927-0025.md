## 需求、现状与方案取舍

目标是同一租户、工作区、幂等键的相同完整请求最多触发一次外部生成；接受后即使任务/计量写库失败，也只能恢复记账。网络超时和 5xx 不能证明供应商未接受。并发量以 16 路争抢同键的真 PostgreSQL 契约验证，不推断生产吞吐量；网络不占用数据库事务。

- 方案一：先调用供应商再按 render_jobs 去重，改动少，但无法阻止两个并发请求先后计费，也不能覆盖 provider 成功、事件写入失败的窗口。否决。
- 方案二：独立提交表预占 + CAS + 先保存 accepted 回执 + 短事务完成业务与事件。多一张表和状态机，未知结果需要对账，但不依赖长事务、供应商幂等支持或超时猜测。本批采用。

## 实现与行为（A）

1. `generation_submissions` 保存 tenant/workspace/project/script/version、幂等键、SHA-256 完整请求指纹、预分配 jobId、owner、provider/model/taskId、receipt、状态、调度次数及时间。唯一约束 `(tenant_id, workspace_id, idempotency_key)`；双作用域 RLS；待核实状态部分索引；触发器验证项目、脚本、版本归属，禁止更换身份/owner、终态重置和 accepted 回执覆盖。
2. `SubmissionLedger.reserve` 先检查旧提交/指纹，再校验数据库脚本正文与完整字段，INSERT ON CONFLICT 后回读并比较；无旧请求指纹的历史 render_jobs 失败关闭。`claim` 仅允许一次 reserved→submitting。provider 调用在短事务外，且必须先完成 dispatch 留痕。
3. 请求指纹覆盖租户、工作区、项目、脚本 ID/版本/正文/字段、目录模型、实际主供应商模型、实际提示词、全部生成参数、mode 和 mock 标记。对象键排序、数组保序，拒绝 NaN/Infinity/BigInt/循环/非普通对象；`__proto__` 作为普通 JSON 键保留。
4. 状态流为 reserved→submitting→accepted→finalized，或 submitting→rejected/unknown。普通异常、断网、5xx、非 JSON、缺任务号均为 unknown；仅明确未接受且允许换链的拒绝可 fallback。已经接受后不再进入 fallback。
5. accepted 先持久化 taskId、实际供应商/模型、实际报价和原始事件。finalize 锁该行，在同一 COMMIT 内写 render_jobs、更新脚本并追加 model.call 与 render.submit。任何一步失败整体回滚；原键重试只补账，保留原调用人。计量 tier 修正为合法 `gen`，档位写入 after.model_tier。
6. accepted 写入确认丢失返回已知 taskId 与 submissionId/key/hash；finalize 确认丢失可回读 finalized。submitting/unknown 不因时间流逝重新 claim；回滚失败销毁连接并同时保留两个异常。
7. 通用 render 路由不再构造只含脚本/模型/时长的窄默认键；档案使用提交服务实际返回的 key/hash。白板使用真实完整脚本行（版本、正文、fields），不伪造 v1。
8. 解说片同一 shotbook 保存不可变的输入指纹与准备参数；重试复用原脚本并直接回到提交账本，不重新配音/装配，不追加版本，不重复审批。改音色、素材、renderScope 或分镜内容会先拒绝。submit/finalize 要求分镜属于当前项目。Remotion provider 同时接受 canonical extra 与已有 CLI 顶层参数，冲突或非法参数在落盘/起进程之前拒绝。

## 接口与异常路径

本批未增加公开 HTTP 路径。`submitGenJob` 返回原字段及 `idempotencyKey`、`requestHash`；`SubmissionError.code` 区分 REQUEST_INVALID、SCRIPT_SCOPE_MISMATCH、SCRIPT_CONTENT_MISMATCH、IDEMPOTENCY_CONFLICT、LEGACY_SUBMISSION_UNVERIFIED、SUBMISSION_IN_PROGRESS、SUBMISSION_UNKNOWN、SUBMISSION_UNVERIFIED、SUBMISSION_ACCEPTANCE_UNVERIFIED、SUBMISSION_FINALIZATION_PENDING。已知回执附 details（submissionId/key/requestHash/taskId/provider），无授权秘密。

base `routeGenSubmit` 新增 `{kind:'unverified', accepted, taskId?, providerId?, error}`；调用方必须按未核实处理，不能当 submitted。trace 异常不再触发备用供应商。

未知回执目前只保存、读取并阻止重发；本卡没有增加自动查单/人工裁决 API。它也不构成统一生产资格、营销 G1、解说片 producer 或 CLI 签章。这些仍由后续独立批完成（D）。本批测试未调用真实模型、不证明成片质量。
