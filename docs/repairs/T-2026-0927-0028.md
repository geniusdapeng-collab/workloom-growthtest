## 需求、选择与落地

目标用户是制作跨空间短片、历史/品牌内容、商品或展示镜头的自动生产任务。解决全局模板覆盖镜头意图、第二空间被室内清单污染、泛型号穿越年代及合法展示被错误拒绝的问题。三个完整场景与字段例子见 environment-realism.md。

候选一继续修补全局关键词例外，改动小但提示词、审计、监制各自漂移；候选二以已有 ShotIntent 为源，增加冻结时代/空间/交互合同，迁移成本是旧卡需写明年代与策略，但可以核对来源和失败边界。本批选择第二种。既有销售 Apple 要求显式迁移成 apple-2024plus，历史/其它品牌使用 story-compatible；未取得故事日期时不取系统时间代填。

- 数据模型：EraProfile（schemaVersion/storyDate/devicePolicy）；每个 Space 独立 materials/practicalLights/traces/colorDiscipline/environmentProfile；PropInteraction 增 purpose/screenFacing；无数据库变更。
- 接口：resolveEraProfile、deviceDefects/devicePolicyStatus/devicePolicyPromptLines；resolveSceneEnvironment/expandShotWithBible；buildPlatePrompt 的 eraProfile/sceneBible options；reviewStage 的 contracts 与 verdict.contractHash；独立 environment CLI v2 报告。
- 正常流程：冻结源事实 → 逐空间展开 → 文本前置校验 → 关键帧实际 prompt → 完整结构化事实送监制 → 媒体证据裁决。合同 hash 是事实绑定，不是生产签章。
- 异常：畸形结构/未知主体/缺日期/未知型号/篡改来源未验证；未来设备/错误类别/朝向矛盾失败；全文超评审预算不截断；审中源合同改变不能继续通过；未知空间不回退。
- 非功能假设：已有本地 JSON 卡规模、无新依赖或网络数据库调用；纯函数不改输入，12 路并发独立；CLI 文件错误 exit2，报告拒绝覆盖原输入；实际媒体审查保持既有资源上限和批次全部通过要求。
- P0：守主体、人数、画幅、灯光、景深，空间隔离，确切设备年代和道具用途；不用会生成违背源卡的画面。
- P1：JSON 幂等展开、贡献来源和合同 hash；不用会把旧增强/变更源合同当本次证据。
- P2：更多有来源的历史型号及材料词表；不做无证据的无限目录。
