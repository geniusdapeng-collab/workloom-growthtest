## 行为变化与依据

- **A｜完整业务结果保留**：启用档案时，`startRun` 不再把 `StageRunner.run` 的归档摘要强转为 `PreproductionResult`。业务结果留在当前尝试的局部变量中，档案仍保存原有摘要。`confirmations` 能继续触发监制打回后的有限重试，`stages.dataMining` 能继续驱动商品摘要与档案投影。
- **A｜失败终态**：`success:false` 对应运行注册表 `failed`，错误原因按异常、`error/errorMessage`、失败数组及被拒确认门提取。成功运行清除旧错误；归档开启/关闭使用同一终态口径。
- **A｜未核实回执重入**：按事件 `seq` 读取每一步最新执行回执，仅 `synced === true` 计为完成。未核实/缺失回执保持 `failed`，不自动重发；当次遇到未核实也立即停止后继步骤。`block/review` 事件仍视为未执行，不占用执行回执状态。
- **A｜边界**：当前 Quest 仍使用位置步骤号；计划内容/审批指纹、工具执行前预占、执行后崩溃对账尚未由本批实现。账本后续同一步真实执行回执会成为最新状态，但本提交没有新增对账 API，不把单测替身当生产对账凭证。

## 用例与实际结果

下表所有模型/供应商/PG 边界均为测试替身；工作器使用实际 `startRun`、`StageRunner`、`ArchiveStore` 与临时文件，Quest 使用实际 `runQuest` 循环。本批没有真实模型或供应商请求。

| 前置条件 | 步骤 | 预期 | 实际 |
|---|---|---|---|
| 档案开启，第一次监制拒绝、第二次成功 | 启动营销预生产，等终态 | 重试两次；商品摘要/投影保持；归档分别 failed/done | 通过 |
| 监制持续拒绝，允许一次重试 | 启动并等终态 | 两次后 failed，保留具体拒绝原因 | 通过 |
| 档案开/关，vendor 返回软失败 | 各启动一次 | 两条路径均 failed，不能 finished | 通过 |
| vendor 抛出错误 | 启动并等终态 | failed、原错误、失败档案、释放租约与绑定 | 通过 |
| vendor 已成功但归档输出写盘失败 | 启动并等终态 | failed、不用内存原始结果伪称成功，释放资源 | 通过 |
| 档案关闭，vendor 成功 | 启动营销预生产 | 成功及商品投影不回归 | 通过 |
| 当前工具回执 false、缺少 synced 或缺少 receipt | 运行两步 Quest，再次重入 | 第一步停线，完成数 0；不执行第二步/不重发第一步 | 通过 |
| 历史回执缺失、空对象、false、字符串 true | 重入 Quest | failed，不执行任何工具 | 通过 |
| 历史全部已核实 | 完成两步后重入 | completed，无重复工具/执行事件 | 通过 |
| 历史只有熔断/待审事件 | 当前围栏放行后运行 | 不将历史门事件误当未核实执行 | 通过 |
| 同一步多个执行回执 | 分别给出成功→未核实、未核实→成功 | 按 seq 使用最新状态 | 通过 |
| 其他租户/工作区/线程存在未核实事件 | 当前范围运行 | 查询使用三个作用域参数，不污染当前任务 | 通过（SQL 边界替身，非实际 RLS 验证） |
| 历史查询报错 | 重入 Quest | 原样上抛，不以空历史执行 | 通过 |
