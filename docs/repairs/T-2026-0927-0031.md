## 需求、假设与取舍

用户场景：① 两个剪辑师同时修改同一包，只允许一个基于当前版本成功；② 页面仍停在 v1，另一人已提交 v2，旧页面必须刷新并核对后提交；③ 本地 FFmpeg 或文件写入失败，重试不得覆盖半成品或伪造成功。

功能要求：前置版本与哈希成对必填；同进程和跨进程互斥；可审计的版本认领与失败；UI、服务、CLI、工具入口同合同。非功能假设：一个包位于同一工位的本地文件系统，单包同一时刻只执行一次返修；工程文件不超过 4 MiB。无新增 DB 表、索引或外部依赖。

候选一：只用进程内 Map 阻止重复作业，改动小，但多服务或 CLI 绕过后无法互斥。候选二：包级独占文件锁 + 工程内容 CAS + 新版本独占目录，跨进程共享同一事实源，代价是异常退出后需核对锁。采用候选二；不宣称网络文件系统的分布式事务或断电持久性保证。

Node 文件标志的独占创建与网络文件系统限制已查官方说明：[Node.js 文件系统标志](https://nodejs.org/docs/latest-v24.x/api/fs.html#file-system-flags)。本地实现与双进程结果为 A/B 证据，网络存储兼容性为 D，不作外推。

## 接口与持久化合同

- `video.delivery.get({dir})`：返回 `revisionBase: {version, projectSha256} | null` 和失败说明 `revisionBaseReason`。读取同一受保护文件描述符的实际字节，校验 schema、项目归属与版本目录。
- `video.delivery.startRevision({dir, patch, expectedVersion, expectedProjectSha256})`：身份来自认证上下文。缺字段或格式错误为 `BAD_REQUEST`，旧快照为 `CONFLICT`。服务在加载工位前后各比较一次，写作业前拒绝冲突。
- CLI：显式双参数 `--expected-version N --expected-project-sha256 HASH`；均省略时只快照用户给定的 `--project`，绝不自动跟随更新版本。`--dry-run` 不写文件，返回选定工程的前置条件。
- `postwrite.reedit`：写请求参数为 `expected_version` / `expected_project_sha256`；`dry_run: true` 可只读取得快照。core 的直接 API 使用 camelCase。
- `.revision.lock`：`wx` 独占创建，0600，记录 runId、pid、host、projectId、基础版本和哈希；只允许持有者按 inode 与 runId 清理。
- `versions/vN/revision-claim.json`：独占认领及目标版本。新目录禁止覆盖，失败编号永不复用。
- `revision.json#commit`：runId、基础版本/哈希、目标版本/工程哈希。临时工程 fsync 后用不可覆盖硬链接发布 `film-project.json`，它是提交点。
- `revision-failed.json`：错误码、消息、基础快照、runId、失败时间。缺少提交工程的版本不作为下一轮基础。

A：`revision_conflict`、`revision_busy`、`revision_io_failed` 不自动切换端点重试。残留锁不凭 PID 自动抢占；需运维核对进程、runId 与产物后恢复，防止误删仍在工作的锁。

## 页面行为与边界

A：返修区显示本次工程基础版本；按钮在快照缺失、JSON 错误、作业运行或请求进行中禁用。提交携带页面已读取的两个前置条件；冲突不会自动刷新哈希后重发。用户点击刷新才重新读取详情，修改内容仍保留以供核对。

A：当前根交付清单和其母版仍代表既有交付版本；新 `film-project` 是返修工程。CAS 小项没有把新工程伪称为已终审的新版母版。新版本工件清单、独立音轨、最终终审封签与选择/入库闭环属于后续已授权的独立交付小项。这个边界须在总任务报告继续追踪，不能据 CAS 完成宣称整条生产链完成。
