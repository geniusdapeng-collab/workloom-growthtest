# WorkLoom Hotel 资产迁移判断与架构方案

> **版本**：v1.0（对焦稿） · 2026-08-25
> **结论先行**：**应该迁，且必须迁**——但不是整库合并，是「三层迁移 + 单 Bundle 承载」。

---

## 一、盘点：workloom-hotel 到底有多"垂直"

把两个仓库的酒店资产逐项对比后，结论很清楚：**workloom 里现有的 hotel bundle 只是早期简化快照，workloom-hotel 才是真正的酒店垂直版**。

| 维度 | workloom-hotel（v2.3.1） | workloom 内置 hotel bundle | 差距 |
|---|---|---|---|
| **围栏基线** | v3，**R1-R20 共 20 条** | v1，R1-R6 共 6 条 | 3 倍+ |
| **官方技能** | **25 个套件**（夜班替代/收益管理/渠道对账/差评危机/语音前台/AI 直播助手/会员CRM/留客经理…） | 3 个 | 8 倍 |
| **数码员工** | **10 员**（多：前台Agent、客房Agent、业主驾驶舱、语音前台Agent） | 7 员 | +4 关键岗位 |
| **对象模型** | **20 类**（room/price_calendar/phone_call/member/campaign/inventory/facility/shift/supplier/invoice/task/alert…） | 8 类 | +12 类 |
| **客群分型** | **三客群默认安装清单**（低星单体"卖 ROI"/民宿"卖自由"/无人酒店"卖远程"）+ 每客群**围栏 patch** + 卖点排序技能清单 | 无 | 这是"配置层个性化"的核心资产 |
| **销售资产** | 一页纸×3 客群、行业落地三技能体系、门店店长指南、新客户接入流程 | 无 | 直接影响签单 |
| **演示系统** | twin 数字孪生演示（simulate/snapshot/restore/genie）+ P13 展示字典层（B 端界面中文化） | 无 | 演示成熟度差距 |
| **种子数据** | 1113 行垂直种子（杭州 86 间房四钻低星单体，含 PMS 厂商字段） | 基础版 | 饱满度差距 |

**两个值得注意的发现：**

1. **hotel 项目自己早就呼唤社媒获客了**——民宿客群的 pitch 里写着「小红书/抖音种草是民宿命脉，权重远高于单体酒店，**前置**」，且技能清单里已有 `content-marketing`、`ai-live-assistant`。你的判断方向与项目自身的演化方向完全一致。
2. **hotel 已有资产与获客方案有天然重叠**——`guest-profile-crm`/`retention-manager`≈住客运营复购、`phone-agent`≈承接环的电话入口、`campaign` 对象已存在。迁移不是"搬运+叠加"，而是**合并设计**，能省掉原计划约 1/3 的新建量。

## 二、判断：迁，按「三层迁移」来

### 为什么不是整库合并

workloom-hotel 的 `apps/web` 有自己的独立演进（p0-p22 页面 + twin 路由 + P13 字典层），workloom 的 web 也有自己的 GEO 剧场演进。两个前端硬合并风险大、收益慢。**资产迁移的正确粒度是 Bundle 配置层 + 数据演示层，前端按需选取。**

### 迁移三层结构

```
第①层 Bundle 配置层（全量升级替换）
  hotel bundle v1 → v3：围栏 R1-R20 + 三客群 patch + segment-defaults
  + 25 技能 + 10 员工 + 20 对象 + stages/archive 升级
第②层 数据与演示层（适配迁移）
  垂直种子（86 间房低星单体）+ 销售文档（一页纸×3/落地向导）
  + P13 展示字典层（评估后并入 workloom web）
第③层 获客层（合并新建）
  承接环 AI 接待 / 线索与券成交 / 团购连接器 / GEO 双域酒店特化
  （与已有 content-marketing/ai-live-assistant/guest-crm 合并设计）
```

### 架构决策：单 Bundle 承载，不是双 Bundle 并行

**决策：酒店工作区只激活一个 `hotel` bundle（v3.0 = 运营域 + 获客域一体），不搞 hotel-ops + hotel-acquisition 两个 bundle。**

理由：
1. **一店一档必须只有一份**——运营数据（房态/差评/对账）和获客数据（线索/成交）在同一个客户档案里才有复购运营的基础；拆两个 Bundle 等于把客户切成两半；
2. **客群分型清单要引用获客技能**——民宿分型已把 content-marketing 前置为旗舰卖点，分型配置必须能统一编排"运营+获客"全部技能；
3. **楼层剧场/战报/围栏瀑布都是单 Bundle 假设**——双 Bundle 要动底座（多 Bundle 工作区），违反「底座零改动」纪律；
4. **geo-growth 保持通用模板**——它是"GEO 代运营"业务线（服务激光机厂商这类客户），酒店 Bundle 把双域能力**特化吸收**（酒店 query 集如「杭州亲子酒店哪家好」、酒店 GEO 图文、酒店能见度词表），两边各自演化，通用能力改进时按同步纪律回灌。

### 与获客五环的关系（修订版）

迁移后，原获客方案 P0/P1 的内容重新映射：

| 原计划 | 迁移后实际要做 | 变化 |
|---|---|---|
| 承接环 AI 接待员 | 扩展已有 `phone-agent`（语音前台）+ `customer-service` 技能为四路承接 | **合并** |
| 住客运营复购 | 已有 `guest-profile-crm` + `retention-manager`，补转介绍激励 | **合并** |
| 直播策划 | 已有 `ai-live-assistant`，补直播卖券 SOP | **合并** |
| 内容店长 | 已有 `content-marketing`，补房态联动排期 | **合并** |
| 线索/券/成交对象 | 新建：lead/lead_event/coupon_sku/booking_order/poi_store/conversion | 新建（核心增量） |
| 外部连接器 | 新建：PMS/抖音本地生活/OTA/企微（mock 先行，种子已有 pms_vendor 字段预留） | 新建 |
| 酒店 GEO 特化 | 新建：酒店 query 集/AI 答案版探店图文/酒店能见度监测（从 geo-growth 特化） | 新建（模式复用） |
| 获客围栏 | 新建：G-ACQ1/2/3 + G-HOTEL1-4（编号空间统一规划） | 新建 |

**净效果：原计划 P0+P1 约 5 周工作量，迁移合并后压缩到约 3.5-4 周。**

## 三、迁移后的系统全貌

```
┌──────────────────────────────────────────────────────────────┐
│            WorkLoom 酒店智能经营系统 v3.0（旗舰）               │
│      「社媒营销 × GEO × 获客 × 酒店运营」深度垂直一体             │
│                                                              │
│  酒店运营域（迁移自 workloom-hotel v2.3.1）                    │
│    夜班替代 · 收益管理 · 渠道对账 · 差评危机 · 语音前台          │
│    前台/客房/巡检 · 三客群分型（低星单体/民宿/无人酒店）          │
│                                                              │
│  酒店获客域（新建，五环闭环）                                    │
│    意图雷达 → 双域触达（短视频+GEO 酒店特化）→ 四路承接          │
│    → 线索分级+券成交 → 归因到钱+复购转介                        │
│                                                              │
│  共用底座：围栏瀑布/事件链/Quest 管线/一店一档/楼层剧场          │
│  外部连接：PMS · 抖音本地生活 · OTA · 企微（mock 先行）          │
└──────────────────────────────────────────────────────────────┘

geo-growth bundle（保留不动）：通用双域模板 + GEO 代运营业务线
ai-video bundle（保留不动）：AI 视频制作经营业务线
```

**价值主张闭环**：「白天空房不用愁——短视频+AI 搜索帮你接客；晚上店长放心睡——夜班+语音前台帮你守店；OTA 佣金不用交——直连成交帮你省钱。」运营域和获客域互相成就，这正是别家 GEO 服务商和酒店 SaaS 都给不了的完整故事。

## 四、风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| **对象模型撞车**：hotel 20 类与 geo-growth 31 类在同一工作区注册，语义冲突（如 campaign） | 中 | 迁移时统一对象注册表，hotel bundle 内获客对象用 `h_` 前缀隔离（如 h_coupon/h_lead）或明确合并语义 |
| **围栏编号空间**：hotel R1-R20 + geo G 系 + 新 G-ACQ/G-HOTEL | 低 | 酒店工作区内统一编号：运营域 R 系不动，获客域新增 R21-R30（连续性比新前缀更符合单调守卫直觉） |
| **员工膨胀**：10 运营 + ~6 获客 = 16+ 员工单工作区，楼层/战报容量 | 中 | P0 迁移后先跑楼层剧场压测；班组编排按客群分型裁剪（民宿不需要客房 Agent，无人酒店不需要前台） |
| **种子事件号段**：ws-yunqi 新旧种子号段纪律 | 低 | 沿用 E-SEED- 前缀 + 回放感知校验器，号段登记表更新 |
| **两边仓库并行演进**：另一个会话也在推进 hotel 仓库 | **高** | 迁移窗口内锁定 workloom-hotel（或 24h 内完成 Bundle 层迁移）；迁移完成后 hotel 仓库打 deprecation 指向 workloom |
| **前端分裂**：twin 演示/P13 字典层在 hotel 侧，GEO 剧场在 workloom 侧 | 中 | P0 不动前端（workloom web 直接消费 hotel 数据）；P1 评估把 P13 字典层并入 workloom web（它是通用能力，hotel 域词表入 hotel bundle） |

## 五、修订后的落地路线

| 阶段 | 周期 | 内容 | 验收 |
|---|---|---|---|
| **P0 酒店资产迁移** | 1 周 | hotel bundle v1→v3 全量替换（围栏/技能/员工/对象/分型/patch）；垂直种子（86 间房低星单体）；销售文档入库；suite + release-gate 全绿 | 酒店工作区三客群分型可一键初始化；楼层剧场 10 员工在岗；验链全绿 |
| **P1 获客层合并新建** | 2.5 周 | 线索/券/成交对象 + 承接环（扩展 phone-agent/customer-service）+ 房态联动内容排期 + 酒店 GEO 特化 + PMS/抖音 mock 连接器 + R21-R30 获客围栏 | 端到端：意图雷达→内容→AI 接待留资→券成交→归因报表；民宿客群分型含获客旗舰技能 |
| **P2 私域复购+归因成交额** | 1.5 周 | 企微连接器 + 转介绍激励 + ROI 账本（含 OTA 佣金节省额）+ 北极星切换 | 战报出「归因成交额」与「佣金节省对比」 |
| **P3 行业模板抽象** | 按需 | 把「运营 Bundle + 获客五环 + 分型配置」抽象为行业垂直方法论，第二行业验证 | 新行业 Bundle 交付 ≤1 周 |

## 六、需要你拍板的四件事

1. **仓库策略**：迁移完成后，workloom-hotel 仓库打 deprecation 声明指向 workloom，停止独立演进——同意吗？（还是保留为"纯运营版"产品线？）
2. **单 Bundle 承载**：酒店工作区一个 hotel bundle 装「运营+获客」全部能力（vs 双 Bundle 要动底座）——同意吗？
3. **围栏编号**：获客域围栏沿用 R 系顺延（R21-R30）而非新前缀——同意吗？
4. **前端策略**：P0 不动前端，P1 再把 P13 字典层并入 workloom web；twin 演示系统是否迁入，等 P0 后评估——同意吗？

> 确认后按 P0→P1 开工，每阶段过 workloom-release-gate 门禁再推送。
