## 二、压测暴露的缺陷与修复（全部已修并回归）

### 🔴 底座级（影响所有行业 Bundle）

**1. 围栏 DSL 能力陷阱：G10 评论分流等规则实战全熔断（最严重）**
- 现象：GEO 套件 B 域 15 个围栏正反例大面积判 block。
- 根因：底座 DSL 只支持算术/比较/abs/min/max——**不支持 `in [...]`、不支持 `contains_any()`**；且「路径不存在即抛错 → 宁可错杀 block」。于是 `params.intent in ['praise','thanks']`（G10a-d）、`contains_any(params.text, [...])`（G10c）、`params.doc_type in [...]`（G15）全部求值异常 → block；`params.involves_persona`（G20）、`params.technique`（G-GEO3）这类稀疏标记字段缺失即爆炸 → 正常发布/回复全被误杀。**ai-video Bundle 的 G10 系列同样踩雷（既有缺陷，此前无实战用例覆盖）。**
- 修复（`packages/base/fence-engine/expr.ts`）：DSL 扩展列表字面量、`in` 运算符、`contains`/`contains_any` 函数；缺失路径在比较/文本语境下宽容为「不命中」，算术与大小比较保持严格（缺数据宁错杀不变）。
- 回归：fence-engine 单测 18 条 + 底座 445 + GEO 77 全绿。

**2. 事件 ID 段撞车：三种子共享租户，ID 段重叠**
- 现象：hotel 种子 100 条事件只落 40 条，验收失败。
- 根因：seed-geo 误用 8800 段（与 hotel 重叠）→ 同租户 `UNIQUE(tenant_id, event_id)` 冲突被幂等丢弃。
- 修复：geo 改 9900 段，并在 seed-geo 头部立「段分配纪律」注释（hotel 8801-8900 / video 6601-6700 / geo 9901-9960）。

**3. agents / triggers 主键跨工作区撞库**
- 现象：ws-geo 只有 12/16 员工、8/14 触发器。
- 根因：agents/triggers 表 PK 是裸 id（`agt-scriptwriter`、`tg-metrics-2h`），与 seed-video 同名撞库被 `ON CONFLICT DO NOTHING` 吞掉——**ws-geo 的 CEO 节拍、指标采集、评论分流触发器实际指向 ws-video**。
- 修复：seed-geo 全部 id 加工作区前缀（`agt-geo-*`、`tg-geo-*`）。

### 🟡 GEO 集成级

**4. 双域作战室不生效**：floor-scene 缺 `ceoDesk/lounge/entrance` 三要素（场景解析器硬性校验）→ 兜底成通用办公区。已补齐，截图实证「WorkLoom GEO·双域作战室」正式上墙。
**5. 评论四档分流无人负责**：GEO 编制没有任何员工绑定 G10a-d → 私域承接专员补绑（其职责本就是评论私信承接）。
**6. 询盘打标逻辑 bug**：`i % 2 === 0` 在 `i % 10 === 2` 场景下恒真 → 60 条事件全部是 AI 搜索入口、社媒入口为零（双入口验证这条 90 天硬指标会直接假死）。已修。
**7. 种子审批幂等缺陷**：`ON CONFLICT (event_id, channel)` 盖不住 `approval_id` 主键冲突 → 复跑即崩。改 `ON CONFLICT (approval_id)`。
**8. 能见度监测官未排夜班**：方案要求夜班接管「GEO 海外平台监测」，preset 却是 `night_shift: false`。已修。

### 🟢 顺带立规
- **G-GEO4 新增**：信源组此前没有日发熔断（社媒有 G9b，信源无对称纪律）→ 新增「单账号信源日发 ≥3 熔断」（信源平台对批量发帖更敏感），围栏总数 16→17，全部文档同步。
- **biz_events RLS 实证**：suite-geo 初期查不到事件（0 行）——不是 bug，是 RLS 要求租户上下文，安全行为得到实测证据（收录为 H-04 用例）。

## 三、业务逻辑审查：不圆融与缺口（按优先级）

### P0 · 建议尽快裁决

**1. 建档期 Agent「有活没人」**
方案第三章一客一档建档写明了四个干活的 Agent：产品理解、市场分析、账号规划、素材理解——但第二章 16 员编制表里**没有这四个人**。D1-D10 建档期是 90 天计划的 W1-W4 主战场，系统里却没有对应的 Quest 管线（4 条管线全是稳态经营，缺第 5 条 onboarding 管线）。三个选项：
- a) 补编 4 员（编制变 18+2）——编制膨胀；
- b) 明确兼任：调研员兼市场分析、实体一致性管理员兼产品理解、数据看板官兼素材理解、公司CEO 兼账号规划（推荐，符合「一人多岗」班组哲学）；
- c) 声明这四个是渠道侧（易飞轮）智能体，不进 WorkLoom 编制——但这样「档案厚度=迁移成本」的写回铁律就出了系统边界。
**我的建议：b + 补一条 `onboarding-archive` 管线（D1-D10 十步），把建档 SOP 落进 Quest 引擎。**

**2. 能见度数据没有结构化时序表**
社媒侧有 `account_metrics` 时序表，GEO 侧的能见度快照目前只以五元事件留痕——**SOV/提及率/首推率趋势图没有查询友好的数据源**，战报 GEO 栏只能回扫事件链。建议加一张 `visibility_metrics`（query/platform/mentioned/first/sov/sentiment/captured_at），否则 W5-W6「能见度周报」落地时会卡。

**3. 集团CEO × 单工作区架构矛盾**
server 身份 scope 绑死单工作区（`scopeOf(identity)`），而 fleet 的核心职责是「跨客户聚合、300 账号一张战报」——**当前架构下 fleet 没有跨 scope 读取通道**。C 类客户（亚凯型 300 账号）是方案里的平台嵌入线主力，这个通道不开，集团CEO 就是空衔。建议：fleet 专用只读聚合视图（`fleet_daily` 已有雏形）+ 显式的跨工作区只读角色。

### P1 · 产品定义缺口

**4. 三端只有两端半**
- **PC B端**（apps/web）：完整可用，双工作区剧场均验证；
- **B端移动**：只有静态 demo（docs/demo/*.html，做得很精致），**生产 web 移动端未适配**（390px 视口实测：头部挤压、卡片溢出，能用但邋遢）；
- **ToC 移动端**：**不存在**。apps/site 是营销落地页，不是产品端。而且 site 的叙事还全是 HyperReality 旧口径，GEO 一点没提。
- 建议先明确「ToC 移动」到底指什么：如果指**客户老板的手机端**（梁老板们批审批、看战报），那就是 B端移动的范畴，把生产 web 做响应式即可；如果真指 C 端消费者触点，那是个新产品线，当前方案里没有它的位置。

### P2 · 顺滑的（确认无问题）

- 五大协同机制在对象/管线/围栏三层都有落点，无「强加戏」——每条协同都能指到具体 Quest step 和围栏编号；
- 围栏体系级别设计自洽：deny 优先并集求值、G20 压 G10a、G-GEO2 压 G-GEO1 都经正反例验证；
- 数据边界红线在 Schema（data_boundary）、宪章 escalate、事件留痕三处一致；
- 数字员工专业度：16 preset 的 prompt 全部三要素（role/goals/constraints）且 goals/constraints 各 ≥2 条（已自动化断言守门）；复用型员工（脚本师等）在 geo 包是简版，**建议后续挂 ai-video 的成熟技能做跨 Bundle 引用**（B-14 用例跟踪）；
- 定价/交付线/客户分层只在文档层（docs/geo-fusion-plan.md），未污染代码——符合「方案是排产文档、代码是经营系统」的边界。
