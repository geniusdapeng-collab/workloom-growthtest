# 返修闭环（反馈 → 分诊 → 层增量重合成 → 回执）

## 一、核心判断：这条反馈是"后期能解决"还是"必须重生成画面"

镜头生成贵、后期便宜，所以反馈进来的**第一件事不是动手，是分诊**：

| 用户说的话（典型） | 归因码 | 受影响的层 | 要不要重生成镜头 |
|---|---|---|---|
| "字幕错别字/时间轴晚了/英文不对/字太小" | `rev.text.track` | text | 否 |
| "配乐太吵/换个曲风/没有节奏感" | `rev.audio.mix` | audio | 否 |
| "太暗/偏黄/想要冷一点/太灰" | `rev.color.look` | color | 否 |
| "转场太生硬/节奏拖/顺序调一下" | `rev.edit.pacing` | assemble → color → audio → text | 否 |
| "封面字太小/换个首图" | `rev.cover.layout` | cover | 否 |
| "标题不够抓人/话题标签换掉/口吻太硬" | `rev.copy.tone` | copy | 否 |
| "第 3 个镜头人物走形了/这个镜头穿帮/画面太糊" | `rev.shot.content` | shots → …（全链重算） | **是**（点名镜头 + G8 人审） |

分诊引擎是**确定性规则表**（`post-bridge/core.mjs#REVISION_RULES`），不依赖 LLM：可复算、可考试、可回归。
认不出是哪一类时返回 `unclear` 并列出可选轴，**不猜**。

## 二、变更影响分析（动手前必须给出这一步）

```bash
post-cli impact --project <交付包>/film-project.json --patch patch.json
```

产出（写进返修记录）：

- `layers`：这次要重算哪些层（`shots → assemble → color → audio → text → cover → copy` 的拓扑序）；
- `localOnly`：能否只做本地重合成（true 即"不重新生成镜头"）；
- `shotRegeneration`：是否需要重生成、点名了哪些镜头、走哪个闸（G8）、为什么；
- `costHint`：本地重合成 = `tokenCostDelta 0`；需要重生成 = `> 0` 且必须先过闸。

**未知的 patch 键直接报错**：看不懂的指令不允许被静默忽略（否则用户以为改了、其实没改）。

## 三、层增量重合成（本地，不重生成镜头）

```bash
post-cli reedit --project <交付包>/film-project.json --patch patch.json
```

- 执行前绑定实际读取的工程版本和 SHA256：工具先用 `dry_run: true` 取得 `expectedVersion` / `expectedProjectSha256`，写请求传 `expected_version` / `expected_project_sha256`；页面按当前详情快照提交，不能默默刷新前置条件。
- CLI `--dry-run` 只读返回前置条件；执行可显式带 `--expected-version N --expected-project-sha256 <sha256>`，省略时仅快照 `--project` 指定文件，过期仍拒绝。
- 并发冲突 `revision_conflict`、占用 `revision_busy`、存储失败 `revision_io_failed` 不自动重试或切换端点；核对现状再提交。
- 输出落**新版本目录**（`versions/v2/`、`v3/`…），旧版本一个字节都不动；
- 只重算受影响层，其余层**按内容哈希复用**（归一化镜头、拼接、调色、混音都有缓存）；
- 回执里逐层写清"重算 / 复用"，复用带 sha256 证据，可与上一版逐项对账（G-DLV7）；
- 包级独占锁 + 新版本目录独占认领；最后发布 `film-project.json` 才算提交。失败目录保留回执、不复用版本号；残留锁由运维核对，不凭 PID 自动抢占。
- 连续返修（v2 → v3）不受影响：每轮工程文件里的路径都按自己的目录重写。
- UHD 工程返修沿用原 `quality` 与逐镜增强来源：未换的镜头复用已归一化产物；换镜头时在本机重新增强并回读目标画布，不把 HD 预览冒充 UHD。

实测口径（真机数据，2026-09-24）：只改字幕的返修**2.4 秒**完成，三个变体的成片文件与上一版**逐字节一致**
（画面根本没被重编码），只有字幕文件与软字幕轨发生变化；全套首次交付（3 镜头 / 27s / 3 变体）约 68 秒。

## 四、确实需要重生成镜头时（花钱路径）

1. 分诊给出点名镜头（`SC-03`、"第 3 个镜头"、"shot 3" 都能认）；
2. `reedit` **拒绝执行**并返回计划（exit 4）：先走渲染链路只重跑被点名的镜头（`render-project.mts --only SC-03`），过 G8 人审；
3. 拿到新镜头产物后，带 `--shot SC-03=<新文件>` 再调 `reedit`：这一步就回到本地合成，未被点名的镜头与全部后期层照旧复用。

**红线**：说不出是第几个镜头就不许整片重跑（G-DLV4 block）；重生成镜头必须人审（G-DLV5 review）。

## 五、返修回执（无回执不算完成）

```json
{
  "schemaVersion": "workloom.delivery-revision/v1",
  "version": 2,
  "commit": { "runId": "本次认领ID", "baseVersion": 1, "baseProjectSha256": "基础工程SHA256", "version": 2, "projectSha256": "新工程SHA256" },
  "patch": { "subtitles": { "zhText": "…" } },
  "impact": { "layers": ["text"], "localOnly": true, "costHint": { "tokenCostDelta": 0 } },
  "rebuilt": [{ "layer": "text", "variant": "warm-story" }],
  "reused":  [{ "layer": "shots", "shotId": "SC-02", "sha256": "…", "note": "复用上次归一化产物（哈希与工程文件一致）" }]
}
```

交付时对用户说清三件事：**改了什么 / 没动什么 / 花了什么**（本地算力 or 渲染额度）。

## 六、经验沉淀（反馈不只用来改这一支片）

| 反馈类型 | 沉淀去哪 | 用途 |
|---|---|---|
| 风格偏好（"喜欢冷调""不喜欢快剪"） | 组织记忆 / 偏好池（主观偏好不进围栏 DSL） | 下一次选变体默认值、变体配方调参 |
| 事实与合规类（参数写错、违禁词） | 缺陷池 / 考试院错题 | 提示词与文案模板加固 |
| 反工归因（哪一层反复被打回） | 岗位绩效 + 错题本 | 该层技能与配方迭代 |
| 变体选择结果（用户最终选了哪个） | 选择事件（`delivery.variant.selected`） | 变体默认集合的长期优化依据 |

## 七、不可修复 / 不该答应的情形（如实回话）

1. **用户要"同一支母版既带硬字幕又不带字幕"** → 不可能：给"软字幕轨版 + 干净版"两支（画面一致）；
2. **原片已带硬字幕又要求再加一层** → 退回上游拿无字母版，不叠字；
3. **素材本身抖动/过曝，用户以为字幕能救** → 记入报告并回退上游，不靠后期掩盖；
4. **要求"重生成整片但只想改一句字幕"** → 先给影响分析：本地改字幕即可，重生成既慢又烧额度；
5. **曲库没有可用曲目** → 报错指名缺什么（可自算作曲兜底），不静默换一首风格不符的。

## 八、质量指标（用于绩效与考试院）

| 指标 | 目标 | 数据来源 |
|---|---|---|
| 返修免重生成率 | ≥ 80% | `revision.json#impact.localOnly` |
| 影响分析准确率（重算层无遗漏/无多余） | 100% | 返修后回归对比 |
| 复用证据完整率 | 100% | `revision.json#reused[].sha256` |
| 返修 turnaround | 本地返修 ≤ 3 分钟（30s 片 / 3 变体） | `revision.json` 时间戳 |
| 二次返修率（同一问题） | ≤ 10% | 反馈归因聚类 |
| 用户变体首次选中率 | ≥ 60% | 选择事件 |

**考试院题目方向**：① "音乐太吵"该走哪条路，为什么不该重生成镜头；
② 用户说"第三个镜头人物走形"，`reedit` 应该做什么、不应该做什么；
③ 只改字幕的返修，哪些文件应该逐字节不变、怎么证明；
④ 返修两次之后发现第二轮的工程文件找不到产物，根因可能是什么；
⑤ 反馈"不够高级"该怎么拆成可执行的层。
